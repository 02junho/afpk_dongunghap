# 02. 이 방향으로 AI가 잘 활용될 수 있는가

결론: **된다. 단, 좁게 써야 한다.** 좁은 게 이 기획의 강점이다.

## AI가 하는 일 3가지

| # | 일 | 입력 | 출력 | 위험도 | 프롬프트 |
|---|---|---|---|---|---|
| 1 | 자유서술 답변의 의미 비교 | 카드 전제 + 답변 A + 답변 B | 전제 대비 편차, A·B 양립 여부, 사유 | 중 | `judge` v2 |
| 2 | 🔴 건 설계사용 요약 | 카드 + 두 답변 + **이미 나온 판정** | 3줄 요약 | 낮음 | `summary` v1 |
| 3 | 설계안 문서 → 카드 초안 추출·분류 | md/docx | 카드 JSON 초안 (설계사 검수 필수) | 중 | `scripts/extract-cards.ts` |

1번은 **`text` 카드에만** 쓴다. number/date/choice는 LLM을 호출하지 않는다.
2번은 판별이 아니라 요약이므로 카드 타입과 무관하지만, **판정을 바꾸지 못한다** — 입력에 판정이
이미 들어 있고, 출력은 설계사가 읽는 문장일 뿐이다. `ENABLE_PLANNER_SUMMARY=1` 일 때만 돈다.

프롬프트가 여러 개이므로 버전도 축이 여러 개다 (`PROMPT_VERSIONS = { judge, summary }`).
상수 하나로 두면 요약 프롬프트를 고쳤을 때 판별 eval 결과가 같이 오염된다.

## AI가 하지 않는 일

- **계산** — 소득 요건, 한도, 월 상환액, 기한. 전부 규칙 기반 엔진
- **판정 기준** — 허용 오차, 🔴 경계는 설계사가 카드에 적는다
- **재무 조언** — 어떤 문장도 AI가 부부에게 "이렇게 하세요"라고 말하지 않는다 (부부는 AI 출력을 아예 보지 않는다)
- **자동 반영** — AI가 추출한 카드 초안은 설계사가 확정하기 전엔 앱에 안 들어간다
- **재설계** — 🔴 이후 연동 수치 재계산은 규칙 엔진(`src/engine`)이, 전제를 어떻게 바꿀지는 설계사가. AI가 재설계하면 이 문서의 주장이 무너진다 (10.14 팀 논의에서 확정)

## 핵심 설계: 2자 비교가 아니라 3자 비교

"남편과 아내가 같은 말을 했나"만 보면 틀린다.

> 남편 "2029년쯤" / 아내 "애 낳고 나서"
> → 둘이 다른가? 2029년에 아이가 있으면 같은 말이다.

그래서 **설계 전제를 기준점**으로 둔다.

```
A vs 전제  →  match / minor / major / unparsed
B vs 전제  →  match / minor / major / unparsed
A vs B     →  양립 가능(true) / 모순(false)
```

`abAgree`는 "같은 문장인가"가 아니라 **"두 답변이 동시에 참일 수 있는가"** 이다.
서로 다른 부분을 말하는 건 불일치가 아니다. 한쪽이 다른 쪽을 부정할 때만 false.
(프롬프트 v1에는 이 정의가 없었고, 그래서 "전세 때 8천 받았다" / "매수 때 1.5억 받는다" 같은
양립 가능한 쌍을 불일치로 떨어뜨렸다. v2에서 명시했다.)

아래는 `src/judge/index.ts` 의 `resolve()` **전체 분기**다. 코드를 바꾸면 이 표도 바꾼다.

| A | B | A·B | 판정 | 의미 |
|---|---|---|---|---|
| unparsed 포함 | | — | 🟡 + 확인 필요 | 해석 불가. 설계사 큐로. match로도 major로도 가지 않는다 |
| match | match | 양립 | 🟢 | 전제 유효, 부부 일치 |
| match | match | 모순 | 🟡 | 둘 다 전제 근처인데 서로 다르다 → 보수적으로 |
| minor | match/minor | — | 🟡 | 한쪽이 흔들림. 다음 라운드에 다시 묻는다 |
| major | 무엇이든 | 양립 | 🔴 **전제 폐기** | 부부는 같은 생각, 설계가 낡음 |
| major | 무엇이든 | 모순 | 🔴 부부 불일치 | 설계사에게 |
| (직전 라운드도 🟡) | | | 🔴 `repeated_yellow` | 2연속 🟡 승격. 조용히 지나가지 않게 |

**한쪽만 major여도 두 사람이 서로 일치하면 '전제 폐기'다.** 부부가 같은 방향으로 움직였는데
"부부 불일치"라고 보고하면, 두 사람 사이를 틀어지게 만드는 오보가 된다.

**"전제 폐기"** 가 이 구조의 보석이다. 부부가 싸우는 게 아니라 설계가 현실을 못 따라온 경우를 따로 잡아낸다. 설계사 체면 문제(설계검토 보완 ⑤)가 여기서 구조적으로 해결된다.

## 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 같은 뜻을 다르다고 (오탐) | **설계사**가 "이건 같은 뜻이에요" → `disputes` + `resolution='false_positive'` → golden set 추가 → 프롬프트 수정. 부부는 판정을 보지 않으므로 설계사가 라벨한다 — 전문가 라벨이라 오히려 낫다 |
| 다른 뜻을 같다고 (미탐) | 🟡 쪽으로 기울이는 프롬프트. 미탐보다 오탐이 낫다 — 오탐은 설계사가 잡는다 |
| 답변을 해석조차 못 함 | `unparsed` → 🟡 + 확인 필요 → 설계사 큐. minor로 위조하지 않는다 (통계가 오염된다) |
| 같은 입력에 다른 답 | 현재 모델(Sonnet 5.5·Opus 5.5)은 temperature 같은 샘플링 파라미터를 **받지 않는다(400)** — 파라미터로 못 박을 수 없으니 `--repeat` 로 **측정**하고 숫자로 낸다. 구조화 출력 + `prompt_version` 저장 |
| 가치관 차이 vs 사실 차이 구분 불가 | AI는 판결하지 않는다. 🟡는 설계사 큐에 안 올리고 다음 라운드에 다시 묻는다(2연속이면 🔴) |

## 부록 3번이 저절로 쌓이는 구조

```
eval/golden.jsonl          답변쌍 + 정답 라벨 (20건, 설계사 오탐 표시로 증가)
eval/run.ts                현재 프롬프트로 전부 돌려 혼동행렬 2개 + 오판 목록 + 자기일관성
eval/__tests__/golden.test.ts  라벨 자체의 모순을 잡는다 (중간 라벨 ↔ 신호등)
judgments.prompt_version   어느 프롬프트가 판정했는지 DB에 남김
judgments.resolution       설계사가 'false_positive'로 닫은 기록 — 전문가 라벨
disputes                   설계사가 "이건 같은 뜻이에요" 누른 기록 (planner_id, 메모)
```

**혼동행렬이 왜 두 개인가.** 최종 신호등만 채점하면, LLM이 `aVsPlan`을 틀렸는데 `resolve()`가
우연히 같은 신호등을 뱉은 경우를 구분할 수 없다. 이 기획의 주장은 "3자 비교"이므로
중간 라벨(편차 3×3)과 신호등(3×3)을 따로 채점한다. `abAgree` 정확도도 따로 낸다.

**자기일관성.** `--repeat=3`으로 같은 입력을 3번 돌려 흔들림을 기록한다. temperature 0 이어도
완전히 결정적이지 않다. "흔들린다"를 숨기지 않고 숫자로 내는 것이 검증이다.

```bash
npm run eval -- --repeat=3     # 실제 LLM
npm run eval -- --mock         # 베이스라인 (키가 있어도 mock 으로)
```

**베이스라인.** `mock`은 LLM이 아니라 토큰 겹침(Jaccard)으로 답한다. 즉 "문자열이 얼마나
비슷한가"만 보는 대조군이다. 같은 golden set에 두 줄을 나란히 놓으면 **"의미 비교에 LLM이
왜 필요한가"가 숫자로 설명된다.** 특히 g15·g17처럼 *서로 다른 말을 하지만 양립 가능한* 쌍은
문자열 유사도로는 원리적으로 풀 수 없다 — 베이스라인이 0/2로 틀리는 것이 정상이고, 그게 근거다.

| 방법 (2026-10-14, 20건×3) | 신호등 | 중간 라벨 | abAgree | 자기일관성 |
|---|---|---|---|---|
| 키워드 겹침 (베이스라인) | 4/20 | 14/40 | 8/20 | — |
| LLM judge v2 · Sonnet 5.5 | 16/20 | 35/40 | 17/20 | 20/20 |
| LLM judge v3 · Sonnet 5.5 | 18/20 | 37/40 | 17/20 | 20/20 |

실행별 상세·오판 분류·남은 라벨 판단은 `docs/05_평가기록.md`. v3 규칙은 이 20건을 보고 만든 것이라
같은 20건의 90%는 과적합이 섞여 있다 — 미학습 케이스를 더한 뒤의 숫자를 보고서에 쓴다.

프롬프트 v1 → v2로 고쳤을 때 정확도가 어떻게 변했는지가 그대로 **"AI 비판적 검증"** 증거다.
다른 팀이 "ChatGPT에 물어봤다"를 쓸 때 우리는 혼동행렬 두 장과 자기일관성을 낸다.

## 솔직한 한계

- text 카드가 5~6장뿐이라 "AI 앱"으로 보이기엔 AI 비중이 작다. → 보고서에서 **의도적으로 작게 썼다**고 먼저 말한다. 환각이 재무설계에 끼어들 자리를 설계로 막았다는 주장이 더 세다.
- 한국어 뉘앙스("좀 무리" vs "감당 가능")는 LLM도 흔들린다. → golden set에 이런 쌍을 일부러 넣어 오탐을 유도하고 기록한다.
- 조건부 date 답변("애 낳고 나서")은 지금 LLM에 넘기지 않고 설계사 큐로 보낸다. 대표 예시를 AI가 직접 비교하게 할지는 docs/04 §B 결정 대기.
