# 06. 보고서 초안 — 앱·AI 부분 (2026-10-16)

> 팀 보고서의 **앱 설명 + AI 활용 + 부록 3번(AI 비판적 검증)** 에 들어갈 글의 초안. 재무설계 본문(1~5단계)은 다루지 않는다.
> 숫자는 전부 `docs/05_평가기록.md` · `eval/results/*.json` 에서 왔다. 화면은 `shots/` (npm run shots).
> 문체는 보고서용으로 다듬기 전이다. 사실 관계만 맞춰 두었다.

---

## 1. 무엇을 만들었나 — 한 문장

재무설계사가 만든 설계안을, 부부 두 사람이 **정말 같게 이해하고 있는지** 주기적으로 확인하는 PWA.
설계안의 전제(가정 카드)를 두 사람에게 **따로** 묻고, 두 답을 **설계 전제와 함께 3자 비교**해 어긋난 곳만 설계사에게 올린다.

- 부부는 결과를 보지 않는다. 앱은 듣고, 설계사가 말한다.
- 설계사가 전제를 고쳐도 바로 전제가 되지 않는다. 부부에게 먼저 묻고, 둘 다 동의해야 바뀐다.
- AI는 자유서술 답변의 **의미 비교**와 **요약**만 한다. 계산·판정 기준·재무 조언·자동 반영·재설계는 하지 않는다.

## 2. 왜 이 형태인가

| 관찰 | 설계로 답한 것 |
|---|---|
| 설계안은 "전제"의 집합인데, 전제는 부부 각자의 머릿속에 다르게 저장된다 ("1.5억 지원"이 한쪽엔 증여, 한쪽엔 차용) | 전제를 **카드 20장**으로 쪼개 하나씩 묻는다 |
| 서로 답을 보면 맞춰 쓴다 | **블라인드** — 상대 답은 끝까지 안 보인다. 대기 화면은 진행 개수만 |
| "같은 말인가"만 보면 틀린다 ("2029년" vs "애 낳고 나서") | **설계 전제를 기준점**으로 둔 3자 비교 → *부부 불일치*와 *전제 폐기*를 가른다 |
| 설계사가 고친 값을 부부가 모른 채 전제가 바뀌면 신뢰가 깨진다 | **먼저 묻기(factcheck)** 라운드 — 둘 다 동의해야 활성화 |
| 설계사는 md·json을 안 쓴다 | 카드 1장씩 폼으로, 사유 한 줄 필수, 모든 변경은 버전으로 남음 |

## 3. 화면 — 부부 5 · 설계사 4

**부부(폰 PWA)**: 입장 코드 → 홈([내 설계] / [맞춰보기]) → 문답(카드 3장, 금액은 단위 버튼, 시점은 연·월 또는 "조건으로 답하기") → 대기(상대 진행만) → 전달 완료.
**설계사(콘솔)**: 커플 목록(코드 발급) → 처리 대기(🔴 + 확인 필요, AI 요약, 버튼 3개) → 가정 카드(수정 → 먼저 묻기) → 변경 이력.

## 4. 판정 — 무엇을 AI가 하고, 무엇을 안 하나

### 4.1 카드 타입 4개 중 AI는 하나

| 타입 | 비교 | 예 |
|---|---|---|
| number | 허용 비율(±%) 안이면 🟢, 두 배 안이면 🟡, 넘으면 🔴 — **규칙** | 목표 주택가격 6억 |
| date | 허용 개월 — **규칙** | 주택 취득 2029-06 |
| choice | 완전 일치 — **규칙** | 육아휴직 주체 |
| text | **LLM 의미 비교** | 승진·이직 계획, 양가 지원, 투자 성향 |

카드 10장 중 text 3장. AI 비중이 작은 것은 의도다 — 환각이 재무설계에 끼어들 자리를 설계로 줄였다.
해석하지 못한 답(모호한 금액, 조건부 시점)은 추측하지 않고 "확인 필요"로 설계사에게 간다.

### 4.2 3자 비교

```
A vs 전제 → match / minor / major      B vs 전제 → match / minor / major      A·B 양립 가능한가
```

| A | B | A·B | 판정 |
|---|---|---|---|
| match | match | 양립 | 🟢 합의 |
| minor 포함 | | | 🟡 다음 라운드에 다시 (아무 화면에도 안 뜸) |
| major 포함 | | 양립 | 🔴 **전제 폐기** — 부부는 같은 생각, 설계가 낡음 |
| major 포함 | | 모순 | 🔴 **부부 불일치** |
| 2회 연속 🟡 | | | 🔴 승격 |

"전제 폐기"가 이 구조의 핵심이다. 부부가 싸우는 게 아니라 **설계가 현실을 못 따라온 경우**를 따로 잡아내 설계사에게 보낸다.

### 4.3 AI가 하는 일 3개 / 하지 않는 일

| 하는 일 | 입력 | 출력 |
|---|---|---|
| ① text 답변 의미 비교 | 전제 + 답 A + 답 B | 편차 2개 + 양립 여부 + 사유 한 문장 |
| ② 🔴 건 설계사용 요약 | 카드 + 두 답 + **이미 나온 판정** | 3줄 (사실 / 영향 / 확인할 질문) |
| ③ 설계안 문서 → 카드 초안 | 문서 | 카드 JSON (설계사 검수 전엔 앱에 안 들어감) |

하지 않는 일: 계산(규칙 엔진), 판정 기준(설계사가 카드에 적음), 재무 조언(어떤 문장도 부부에게 가지 않음), 자동 반영, 재설계.

## 5. 부록 3번 — AI를 어떻게 검증했나

### 5.1 방법

- **golden set 30건**: 답변쌍 + 정답 라벨(최종 신호등 + 중간 라벨 3개). 라벨끼리 모순이면 테스트가 잡는다.
- **혼동행렬 2개**: 신호등(3×3)과 편차(3×3)를 따로 채점한다. 최종 신호등만 보면 중간 라벨이 틀렸는데 운으로 맞은 경우를 못 가른다.
- **자기일관성**: 같은 입력을 3회 돌려 흔들림을 기록한다. 현재 모델은 temperature 를 받지 않으므로 파라미터로 못 박을 수 없고, 측정만 할 수 있다.
- **베이스라인**: LLM 없이 토큰 겹침(Jaccard)으로 답하는 대조군. "의미 비교에 LLM이 필요한가"의 근거.
- **미학습 집합**: 프롬프트 규칙을 만든 **뒤에** 쓴 10건으로 다시 잰다. 규칙을 만들 때 본 20건의 점수는 과적합이 섞여 있다.

### 5.2 결과 (2026-10-14, Claude Sonnet 5.5, 각 3회)

| | 신호등 | 중간 라벨 | abAgree | 자기일관성 |
|---|---|---|---|---|
| 베이스라인(키워드 겹침) · 30건 | 6/30 (20%) | 19/60 (32%) | 10/30 | — |
| 프롬프트 v2 · 20건 | 16/20 (80%) | 35/40 (88%) | 17/20 | 20/20 |
| 프롬프트 v3 · 30건 | 26/30 (87%) | 52/60 (87%) | 28/30 | 30/30 |
| **프롬프트 v3 · 미학습 10건** | **8/10 (80%)** | **14/20 (70%)** | 9/10 | 10/10 |

보고서에 쓰는 숫자는 **미학습 10건의 80% / 70%** 다. 베이스라인 대비 4배.

### 5.3 v2 → v3: 무엇을 고쳤고 무엇이 나빠졌나

v2 오판 6건을 읽고 **프롬프트 탓인 3건만** 일반 규칙으로 고쳤다 (케이스를 지목하지 않음):
① 구어체 완화("한 1억 5천?")는 유보가 아니다 ② 부분적 제안("일부는 ETF 해도")은 뒤집은 게 아니라 흔들린 것 ③ 전제에 합의가 있으면 합의가 선호보다 기준.
결과: 2건 맞아지고 **1건 틀어짐**. 라벨이 다툼의 여지가 있는 3건은 모델에 맞춰 고치지 않고 규칙서 기준으로 재검토했다.

### 5.4 미학습 10건에서 배운 것

- **오탐이 미탐보다 많다** (설계 의도). 부서 이동을 "변화"로 읽어 🟡 — 큐엔 안 가고 다음 라운드에 다시 묻는다.
- **abAgree 정의의 구멍**: "남편이 주택자금 절반을 친구 사업에 투자" / "아내는 상의 못 받았다" — 두 문장은 동시에 참이라 '양립'으로 읽혔다. 설계사가 보려는 건 사실의 양립이 아니라 **입장의 양립**이다. → 프롬프트 v4 후보. 단 같은 10건으로 재면 더는 미학습이 아니므로, 새 케이스를 쓴 뒤 잰다.
- **실행 간 흔들림**: 한 실행 안의 자기일관성 30/30이 실행 간 일관성을 보장하지 않았다 (같은 케이스가 오전 🟢, 오후 🟡). 경계 케이스는 날을 달리해 두 번 잰다.

### 5.5 오탐이 데이터가 되는 구조

설계사가 큐에서 **[이건 같은 뜻이에요]** 를 누르면 그 건이 `disputes` 에 남는다. 재무설계사가 직접 라벨링한 오탐 — golden set 최고 품질 소스. 어느 프롬프트 버전이 판정했는지(`prompt_version`)가 모든 판정에 남으므로, 버전을 올릴 때마다 같은 집합으로 다시 잴 수 있다.

## 6. 솔직한 한계

- 카드 10장은 데모용 세트다. 설계안 문서에서 카드를 뽑는 UI는 공모전 범위 밖(스크립트만).
- 설계사 인증은 코드 하나(임시). 부부 인증은 익명 로그인 + 입장 코드.
- text 카드가 3장뿐이라 AI 비중이 작다 — 의도적으로 작게 썼다.
- 한국어 뉘앙스("좀 무리" vs "감당 가능")는 LLM도 흔들린다. golden set에 일부러 넣어 기록했다.
- 제도 수치(소득 상한·한도·금리)는 `programs.ts` 한 곳에 출처·확인일과 함께 두었다. L1 재확인은 제출 전 필수.

## 7. 기술 (한 줄씩)

Vite + React PWA / Supabase(Postgres·RLS·익명 로그인) / Vercel(엣지 함수가 LLM·DB 서버 키를 쥠, 브라우저엔 키 없음) / Claude Sonnet 5.5 / 테스트 67건 / 부부는 상대 답·판정을 읽을 DB 정책 자체가 없다 — 블라인드는 클라이언트 선의가 아니라 DB가 보장한다.
