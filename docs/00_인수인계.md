## 다음 할 일 (우선순위)

**P0 — 먼저 결정해야 움직이는 것**

1. **`.env`에 LLM 키 넣고 `npm run eval -- --repeat=3`** → `eval/out/v2-*.json`. 이게 부록 3번의 첫 줄이다.
   혼동행렬 2개(신호등·중간 라벨)와 자기일관성이 같이 나온다. 오탐 목록 보고 golden 추가.
2. **판정을 서버로 옮긴다.** 지금은 브라우저가 양쪽 답변을 다 쥐고 결정적 비교를 한다 →
   "상대 답은 둘 다 제출한 뒤에만 보인다"를 DB로 보장할 수 없다. `/api/judge` 가
   `{roundId, cardVersionId}` 를 받고 service_role 로 answers 를 읽어 판정·기록하게 바꾸면,
   부부에게 answers select 를 아예 닫을 수 있다 (`supabase/rls.sql` 머리말).
3. **Supabase 프로젝트 생성 → `schema.sql` → `rls.sql` → `seed.sql`.** `.env`에 URL·anon key.
   SQL 은 아직 한 번도 실행된 적이 없다 — 첫 적용에서 오류가 날 수 있다.
4. **익명 로그인 + 설계사 이메일 로그인.** 부부는 Supabase anonymous sign-in → `join_couple()` RPC 로
   `members.auth_user_id` 연결 (코드 6자리 입력이라는 체감은 그대로). 이게 없으면 RLS를 걸 수 없다.

**P1 — 화면 실연결**

5. 설계사 화면 — `/p/cards` 저장 → `card_versions` insert(version+1, reason 필수) →
   `rounds` kind='reconfirm'. `/p/queue` ← `planner_queue` 뷰. 닫을 때 `resolution` 필수.
6. 부부 화면 — `/c/join` → `join_couple()`. `/c/round` → `answers` insert.
   상대 제출 전 잠금은 **3초 폴링**으로 먼저 (Realtime 은 RLS와 엉켜 시간을 먹는다).
7. 결과 → `judgments` 저장(답변 스냅샷 포함) + 🔴면 `planner_summary` 생성.
8. "이건 같은 뜻이에요" → `disputes` insert. eval 러너가 disputes 를 읽어 golden 후보로 출력.

**P2 — 여유 있으면**

9. 푸시 1회 시연용 (Web Push, VAPID). **iOS PWA는 홈 화면 추가 + 권한이 필요해 시연 실패 확률이 높다.**
   반나절 넘기면 접고 화면 캡처로 설명한다.
10. Vercel 배포 (`ALLOW_DEMO_JUDGE=0` 확인). 폰 2대로 리허설.

시험기간이 끼면 1·3·4가 쪼개기 쉽다.

## 설계사 페이지 = "관리자" 페이지에 대해

맞는 방향이고 이미 그 구조다(`/p/*`). 4화면 전부 만들어 뒀다.

- **UI에서 "관리자"라는 말을 쓰지 않는다.** "설계사 콘솔"로. 심사위원이 재무설계사다.
- **설계사 1명 : 커플 N쌍.** 첫 화면은 `/p/couples` — 커플을 고르면 그게 나머지 화면의 컨텍스트다.
- **커플 발급**도 설계사가 한다 — `/p/couples` 에서 코드 6자리 생성. PWA 홈 화면 추가 안내도 여기서.
- **사용친화의 핵심은 '파일을 안 만진다'는 것.** 카드 1장씩 폼으로, 사유 한 줄 필수, 저장하면 끝.
- 허용 범위 입력은 **타입별로 단위를 다르게** 보여준다 (number ±%, date ±개월).
  한 칸에 0.05와 6을 받으면 반드시 사고가 난다.

## 결정 사항 (바꾸려면 이유를 docs에 먼저)

| 결정 | 이유 |
|---|---|
| PWA, 네이티브 아님 | 심사 장면이 "URL 열고 폰 2대". 설계사 경유 설치라 iOS 홈화면 추가 깔때기가 온보딩에 흡수됨 |
| 3자 비교 (A·B vs 전제) | 2자 비교는 "2029년" vs "애 낳고 나서"를 못 가른다. 전제를 기준점으로 두면 `plan_stale`이 생김 |
| 판별은 text만 LLM | 환각이 낄 자리를 설계로 줄임. 20장 중 5~6장 |
| 요약(AI 2번)은 카드 타입 무관 | 🔴 건에만, `ENABLE_PLANNER_SUMMARY=1` 일 때만. 판별이 아니므로 환각이 전제를 바꾸지 못한다 |
| 오탐 > 미탐 | 오탐은 사용자가 이의 제기로 잡고 그게 데이터가 됨. 미탐은 조용히 지나감 |
| 모호한 입력은 파싱 실패(🟡) | 조용히 틀린 숫자가 🟢/🔴이 되는 것이 더 나쁘다. '6천'은 6천원인지 6천만원인지 모른다 |
| 카드 버전, md 교체 아님 | 정체성 유지·부분 갱신·설계사가 md 안 씀 |
| 갱신 시 해당 카드만 재합의 | 설계사 수정도 부부 동의를 거쳐야 전제가 됨. 루프가 닫힘 |
| 부대비용 1,200만 명시 필드 | 필요대출 3억 6,248만의 구성. 숨은 가정 금지 |
| 한쪽만 major 라도 서로 일치하면 plan_stale | 부부가 같은 생각인데 "부부 불일치"로 보고하면 안 된다 |
| 2연속 🟡 → 🔴 (`repeated_yellow`) | 조용히 지나가는 🟡을 막으면서 설계사 개입 건수는 줄인다 |

## 알려진 구멍

- **SQL 3종이 한 번도 실행되지 않았다.** 첫 적용 때 오류가 날 수 있다. 특히 트리거·뷰.
- `parseYearMonth`는 "봄/가을", "애 낳고" 같은 표현을 못 푼다 → `unparsed` → 🟡 + needsReview.
  date 카드는 연·월 선택 UI로 바꿨지만, `allowCondition` 카드는 **조건으로 답하는 길을 남겼다**
  (docs/02 의 대표 예시가 거기서 산다). 지금은 조건부 답변을 LLM에 넘기지 않는다 — docs/04 참조.
- 금액은 단위 버튼 + 원 단위 미리보기로 입력받는다. 그래도 자유 입력이 오면 모호한 값은 NaN이다.
- mock LLM은 20건 중 4건 맞힌다. 당연함. **품질 측정에 쓰지 말 것.**
- `eval/run.ts`는 golden의 `cardKey`를 `seed-cards.json`에서 찾는다. 카드 key 바꾸면 golden도
  (테스트가 잡아준다).
- 증여재산공제 2년 창구는 조문 L1 미확인. `deadlines.ts` 주석 참조.
- `programs.ts`의 `sourceUrl`이 루트 도메인뿐이다. **심사위원이 재무설계사다** — 고시 페이지
  deep link + 캡처를 `docs/`에 넣고 2026년 기준 수치를 L1에서 재확인할 것.
