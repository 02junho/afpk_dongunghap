# 03. 재무설계사는 앱을 어떻게 갱신하는가

## 질문: md 파일 교체인가?

**아니다.** 세 가지 이유.

1. **카드 정체성이 깨진다.** v1의 "주택 취득 시점"과 v2의 "주택 취득 시점"이 같은 카드라는 걸 파일 교체로는 보장 못 한다. 정체성이 깨지면 답변 이력·판정 이력이 전부 끊긴다.
2. **전부 아니면 전무.** 카드 1장 고치려고 문서 전체를 다시 올리면, 바뀌지 않은 19장도 "변경됨"으로 보인다. 부부에게 무엇이 바뀌었는지 말할 수 없다.
3. **설계사는 md를 안 쓴다.** 현업은 한글·워드·PDF다. 파일 포맷에 기대는 순간 "실제로 돌아가나"에서 막힌다.

## 답: 카드는 버전을 가진다

```
cards           정체성 (couple_id + key)       ← 바뀌지 않음
card_versions   값·허용범위·사유·작성자·시각    ← 수정할 때마다 1행 추가
```

설계안 "문서"는 `plan_documents`에 첨부로 둔다. 참고용이다. 앱은 읽지 않는다.

## 최초 입력

| 방법 | 3주 안에 | 설명 |
|---|---|---|
| **A. 폼 입력** | ✅ | `/p/cards`에서 카드 1장씩 추가 |
| **B. seed JSON** | ✅ | 데모용. `src/data/seed-cards.json` → `supabase/seed.sql` |
| C. 문서 업로드 → AI 초안 추출 → 검수 | △ 스크립트만 | `scripts/extract-cards.ts`. UI는 공모전 후 |

C가 "md 교체"의 올바른 형태다. **문서가 앱을 갱신하는 게 아니라, 문서에서 카드 초안을 뽑고 설계사가 확정한다.** AI 활용 3번이기도 하다.

## 갱신 흐름 (🔴 발생 시) — 10.14 팀 확정

```
1. 🔴 판정 → judgments 저장 → 설계사 큐 (카테고리 · 전제 · 두 답변 · AI 요약)
2. 설계사가 고른다
   ├─ [두 분께 먼저 묻기]  그 카드 하나로 factcheck 라운드 생성
   │     질문: "이 전제가 맞나요? 이걸로 설계를 조정해도 될까요?"
   │     둘 다 답하면 → 설계사가 값 수정 + 사유(필수) → card_versions 새 행
   │     → 연동 수치는 규칙 엔진이 재계산 (AI 아님) → 설계사 확인 → 활성
   └─ [상담 때 다루기]  큐에 보관, 다음 상담 안건. 앱 밖에서 다룬다
3. 부부에게 푸시: "설계사가 '승진·이직 계획'을 수정했어요. 사유: …" + [내 설계]에 반영
4. 다음 정기 라운드부터 새 전제로 질문
```

**"재합의"와 "사실 확인"은 같은 장치다** — factcheck 라운드 하나. 설계사가 전제를 바꾸려면 먼저 두 분께 묻고, 둘 다 답해야 바꿀 수 있다. 설계사가 고쳤다고 끝이 아니라 부부를 거쳐야 전제가 된다. 루프가 닫힌다.

버튼 이름이 "카드 고치기"였던 것을 "두 분께 먼저 묻기"로 바꿨다 — 비전공 팀원이 뜻을 못 알아들었고, 실제 동작도 "먼저 묻기"가 맞다.

## 설계사가 고칠 수 있는 것 / 없는 것

| 고칠 수 있음 | 고칠 수 없음 |
|---|---|
| 전제 값 (planned_value) | 부부의 답변 |
| 허용 범위 (tolerance) | AI 판정 결과 (이의 제기는 부부 몫) |
| 카드 추가·보관(archive) | 과거 버전 (삭제 불가, 이력) |
| 질문 문구 | |

## 갱신 없이 끝나는 경우

🟢·🟡는 설계사 큐에 안 올라온다. 부부도 판정을 보지 않으므로 🟡는 아무 화면에도 안 뜨고, 다음 라운드에 같은 카드를 다시 묻는다. 2연속 🟡면 🔴로 승격해 큐에 올린다. 설계사 개입 건수를 줄이는 장치다.
