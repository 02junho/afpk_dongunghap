# 01. 앱 구성과 현실적인 방향

## 역할 3개, 화면 2벌

| 역할 | 기기 | 하는 일 |
|---|---|---|
| 설계사 | 데스크톱 웹 `/p/*` | 카드 입력·수정, 🔴 큐 처리, 오판 표시, 변경 이력 확인 |
| 남편 | 폰 PWA `/c/*` | 블라인드 답변, [내 설계] 확인. **결과는 보지 않는다** |
| 아내 | 폰 PWA `/c/*` | 동일 |

한 코드베이스, 라우트로 분리. 부부 화면은 폰 폭(390px) 기준, 설계사 화면은 데스크톱 기준.

## 진실의 원천은 카드

```
설계안(문서) ──▶ 카드 20장 ──▶ 라운드 ──▶ 답변 ──▶ 판정 ──▶ (🔴) 설계사 ──▶ 먼저 묻기 ──▶ 카드 수정
   참고용         원천                                                              │
                   ▲                                                                │
                   └────────────────────────────────────────────────────────────────┘
```

문서는 참고 자료다. 앱이 읽는 건 **카드**뿐이다. 카드가 바뀌면 다음 라운드가 자동으로 새 전제를 묻는다.

## 카테고리 8개 → 세부 카드

큰 묶음은 팀이 정한다: **주거 / 소득·직업 / 출산·양육 / 양가 지원 / 저축·투자 / 보험 / 은퇴 / 세금** (AFPK 7과목 + 양가). 그 안의 세부 전제(카드)는 설계안 문서에서 AI가 뽑아 분류하고(`scripts/extract-cards.ts`, 초안), 설계사가 검수·확정·추가한다. 시드 10장은 데모용이지 상한이 아니다.

## 카드 타입 4개 — AI는 하나에만 개입

| 타입 | 예 | 입력 UI | 비교 방식 |
|---|---|---|---|
| `number` | 목표 주택가격 6억 | 숫자 + 단위 버튼, 원 단위 미리보기 | 허용 **비율**(±%) 내 결정적 비교 |
| `date` | 주택 취득 2029년 | 연·월 선택 (+ 조건으로 답하기) | 허용 **개월** 내 결정적 비교 |
| `choice` | 육아휴직 주체: 아내 | 선택 | 완전 일치 |
| `text` | 승진·이직 계획 | 자유 서술 | **LLM 의미 비교** |

- `number` 카드는 `unit`을 가진다 (`krw` / `age` / `count` / `percent`). 같은 number라도
  "60"은 나이로는 60이지만 금액으로는 60원일 수 없다 — 파싱·표시 규칙이 다르다.
- `tolerance`는 타입에 따라 의미가 다르다 (number는 비율 0.05, date는 개월 6).
  설계사 화면에서 **단위를 타입별로 다르게 표시**한다.
- 해석하지 못한 답변은 `unparsed` → 🟡 + `needs_review` → 설계사 큐. **minor로 위조하지 않는다.**

카드 20장 중 text는 5~6장이다. AI가 끼는 비율이 낮은 게 약점이 아니라 **강점**이다. "어디서 AI가 틀릴 수 있는지"를 정확히 말할 수 있다.

## 화면 목록

**부부 (5)** — 결과는 보지 않는다. *앱은 듣고, 설계사가 말한다.* (10.14 팀 결정)
1. `/c/join` — 입장 코드 6자리, 남편/아내 선택. "답변은 설계사만 봅니다" 고지
2. `/c/home` — 탭 두 개. **[내 설계]** 설계사가 잡은 전제를 평소에 보는 화면(카테고리 타일 + 진척률) / **[맞춰보기]** 점검 질문 입구, 점검 시기엔 빨간 점
3. `/c/round/:id` — 카드 3장 순서대로 답변. 상대 답변 안 보임. 제출 후 수정 불가
4. `/c/wait/:id` — 상대 진행 상태만 (답 내용 없음. 개수만 주는 `round_progress()` RPC)
5. `/c/done/:id` — "두 분 답변이 설계사님께 전달됐어요". 판정도 상대 답도 없음. 다음 맞춰보기 안내

**설계사 콘솔 (4)** — UI에서 "관리자"라 쓰지 않는다
1. `/p/couples` — 담당 커플 목록 + 새 커플(입장 코드 발급). 여기서 커플을 고르면 아래 화면의 컨텍스트가 됨
2. `/p/queue` — 🔴 전부 + 자동 판정이 안 된 🟡(확인 필요). 카테고리 · 전제 · 두 답변 · AI 요약. 버튼 **[두 분께 먼저 묻기] [상담 때 다루기]** + **[이건 같은 뜻이에요]**(AI 오판 표시 — 부부가 아니라 설계사가 누른다). 어느 버튼으로 닫았는지가 `resolution` 으로 남는다
3. `/p/cards` — 카테고리별 카드 목록. 클릭 → 값·허용범위·조건부 허용·사유 수정 → "두 분께 먼저 묻고 v2 저장" → factcheck 라운드 → 둘 다 동의 시 활성
4. `/p/history` — 누가 언제 무엇을 왜 바꿨는지 (읽기 전용)

## 3주 범위

| 만든다 | 안 만든다 |
|---|---|
| 입장 코드 연결 (익명 로그인) | 회원가입·비번찾기·프로필 |
| 1라운드 3장 블라인드 | 월 1회 스케줄러 |
| 결정적 비교 + text LLM 비교 (서버에서) | 20장 전부 |
| 전달 완료 화면 (결과 없음) | 결과 화면 — 10.14 폐기 |
| [내 설계] 탭 (카드 타일 + 진척률 1개) | 설계안 문서 뷰어 |
| 설계사 콘솔: 커플 발급·큐·카드 수정·오판 표시·이력 | — |
| 카테고리 8개 + 카드 10장 시드 | 설계안→카드 추출 UI (스크립트만) |
| 상대 제출 대기 (3초 폴링) | Realtime 구독 |
| 제도 계산 엔진 + 테스트 | 계산 UI |
| (여유 있으면) 푸시 1회 시연 | 푸시 스케줄링 |

## 디자인 방향 (10.14)

둥글고 따뜻하게. 부부 쪽은 토스처럼 긴장을 낮추는 문법, 설계사 쪽은 같은 색으로 차분하게.
- **두 개의 동그라미**가 표식. 남편 하늘색 `--him` / 아내 복숭아색 `--her`. 대기 화면에선 한쪽이 비고, 전달되면 둘이 붙는다
- 바탕 `--paper #fff7f2`(복숭아빛 흰색), 모서리 20px, 그림자 부드럽게
- 제목·질문은 **고운돋움**(둥근 고딕), 본문은 Pretendard. 명조는 뺐다
- 판정은 채운 칩(연한 바탕 + 진한 글자). 설계사 콘솔에서만 보인다
- 베러웰스(FA용, 파란 SaaS 문법)·토스(파란 CTA)와 겹치지 않게 **파랑을 주색으로 쓰지 않는다**
- PWA 아이콘도 같은 두 동그라미. `node scripts/make-icons.mjs` 로 생성 (의존성 없음)

## 스택

Vite + React + TypeScript / vite-plugin-pwa / Supabase (Postgres·Auth) / Vercel (호스팅 + 서버리스 `api/judge`) / Vitest / Playwright (스크린샷만)

LLM 키는 브라우저에 두지 않는다. `api/judge.ts`가 유일한 호출 지점이고,
`npm run dev`에서는 vite 미들웨어(`vite.config.ts`)가 같은 일을 node 쪽에서 한다.
`src/judge/text-llm.ts`는 브라우저에서 import 하지 않는다 — 빌드 산출물에 `api.anthropic.com`
문자열이 없는지 확인할 수 있다.
