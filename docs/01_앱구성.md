# 01. 앱 구성과 현실적인 방향

## 역할 3개, 화면 2벌

| 역할 | 기기 | 하는 일 |
|---|---|---|
| 설계사 | 데스크톱 웹 `/p/*` | 카드 입력·수정, 🔴 큐 처리, 변경 이력 확인 |
| 남편 | 폰 PWA `/c/*` | 블라인드 답변, 결과 확인, 이의 제기 |
| 아내 | 폰 PWA `/c/*` | 동일 |

한 코드베이스, 라우트로 분리. 부부 화면은 폰 폭(390px) 기준, 설계사 화면은 데스크톱 기준.

## 진실의 원천은 카드

```
설계안(문서) ──▶ 카드 20장 ──▶ 라운드 ──▶ 답변 ──▶ 판정 ──▶ (🔴) 설계사 ──▶ 카드 수정
   참고용         원천                                                    │
                   ▲                                                      │
                   └──────────────────────────────────────────────────────┘
```

문서는 참고 자료다. 앱이 읽는 건 **카드**뿐이다. 카드가 바뀌면 다음 라운드가 자동으로 새 전제를 묻는다.

## 카드 타입 4개 — AI는 하나에만 개입

| 타입 | 예 | 입력 UI | 비교 방식 |
|---|---|---|---|
| `number` | 목표 주택가격 6억 | 숫자 + 단위 버튼, 원 단위 미리보기 | 허용 **비율**(±%) 내 결정적 비교 |
| `date` | 주택 취득 2029년 | 연·월 선택 (+ 조건으로 답하기) | 허용 **개월** 내 결정적 비교 |
| `choice` | 육아휴직 주체: 아내 | 선택 | 완전 일치 |
| `text` | 승진·이직 계획 | 자유 서술 | **LLM 의미 비교** |

- `number` 카드는 `unit`을 가진다 (`won` / `age` / `count` / `percent`). 같은 number라도
  "60"은 나이로는 60이지만 금액으로는 60원일 수 없다 — 파싱 규칙이 다르다.
- `tolerance`는 타입에 따라 의미가 다르다 (number는 비율 0.05, date는 개월 6).
  설계사 화면에서 **단위를 타입별로 다르게 표시**한다. 한 칸에 0.05와 6을 받으면 사고가 난다.
- 해석하지 못한 답변은 `unparsed` → 🟡 + `needs_review`. **minor로 위조하지 않는다.**

카드 20장 중 text는 5~6장이다. AI가 끼는 비율이 낮은 게 약점이 아니라 **강점**이다. "어디서 AI가 틀릴 수 있는지"를 정확히 말할 수 있다.

## 화면 목록

**부부 (5)**
1. `/c/join` — 커플 코드 6자리 입력, 역할 선택
2. `/c/home` — 다음 라운드 안내, 합의율, 진척률
3. `/c/round/:id` — 카드 3장 순서대로 답변. 상대 답변 안 보임. 둘 다 제출 전까지 잠김
4. `/c/result/:id` — 카드별 🟢🟡🔴. 🟡엔 대화 유도 문장. 🔴엔 "설계사에게 전달됨".
   🟢이 아닌 모든 건에 이의 제기 버튼 (결정적 판정도 오탐이 난다)
5. 이의 제기 — 결과 화면 안에서 처리. 별도 라우트를 두지 않는다

**설계사 콘솔 (4)** — UI에서 "관리자"라 쓰지 않는다
1. `/p/couples` — 담당 커플 목록 + 새 커플(코드 발급). 여기서 커플을 고르면 아래 화면의 컨텍스트가 됨
2. `/p/queue` — 🔴 전부 + 자동 판정이 안 된 🟡. AI 요약 + 두 답변 + 현재 전제.
   닫을 때 **이유를 남긴다**: 카드 수정 / 오탐이었다 / 조치 불필요
3. `/p/cards` — 카드 목록. 클릭 → 값·허용범위·조건부 허용·사유 수정 → 새 버전 → 재합의 라운드
4. `/p/history` — 누가 언제 무엇을 왜 바꿨는지 (읽기 전용)

## 3주 범위

| 만든다 | 안 만든다 |
|---|---|
| 커플 코드 연결 | 회원가입·비번찾기·프로필 |
| 1라운드 3장 블라인드 | 월 1회 스케줄러 |
| 결정적 비교 + text LLM 비교 | 20장 전부 |
| 결과 화면 + 이의 제기 | 진척률 그래프 |
| 설계사 콘솔: 커플 발급·큐·카드 수정·이력 | — |
| 상대 제출 전 잠금 (3초 폴링) | Realtime 구독 |
| 제도 계산 엔진 + 테스트 | 계산 UI |
| (여유 있으면) 푸시 1회 시연 | 푸시 스케줄링 |

## 스택

Vite + React + TypeScript / vite-plugin-pwa / Supabase (Postgres·Auth) / Vercel (호스팅 + 서버리스 `api/judge`) / Vitest

LLM 키는 브라우저에 두지 않는다. `api/judge.ts`가 유일한 호출 지점이고,
`npm run dev`에서는 vite 미들웨어(`vite.config.ts`)가 같은 일을 node 쪽에서 한다.
`src/judge/text-llm.ts`는 브라우저에서 import 하지 않는다 — 빌드 산출물에 `api.anthropic.com`
문자열이 없는지 확인할 수 있다.
